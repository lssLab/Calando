# Codex Desktop Appの監視

<p align="center">
  <a href="codex-app.md">English</a> · <a href="codex-app.ko.md">한국어</a> · <a href="codex-app.zh-CN.md">简体中文</a> · <strong>日本語</strong>
</p>

Codex Desktop App は Codex CLI と同じ保護ポリシーを使用しますが、プロセス構造が異なります。 この文書では、何を正確に測定できるか、どこを制御の対象にすることができるか、およびApp Serverが所有権の証拠を十分に明らかにしない場合にsupervisorがどのように保守的であるかを説明します。

<a id="cli-and-desktop-app-are-not-the-same-process-model"></a>
## CLI とデスクトップ アプリは同じプロセス モデルではありません

CLI セッションには通常、lead プロセスと、1 つのローカル実行ユニットとして測定および再検証できるプロセス ツリーがあります。 デスクトップ アプリは通常、1 つの App Server プロセスを通じて複数の会話をルーティングします。

各会話には論理スレッド識別子があり、hook の決定に対して独立した lead として管理されます。 これは独立したオペレーティング システム プロセスではありません。

```text
Codex Desktop App
        │
        ▼
shared App Server process and shared memory
        │
        ├── logical thread A ── agents and tools
        ├── logical thread B ── agents and tools
        └── unassigned App work ── ownership not yet proven
```

同じ会話を別のウィンドウで開いても、別の論理的な lead は作成されません。 別の会話を開くと別の論理スレッドが作成されますが、両方とも同じ App Server メモリを共有する可能性があります。

<a id="what-the-supervisor-observes"></a>
## supervisor が観察しているもの

ローカルの daemon は App Server を検出し、そのメモリを 1 回記録します。 Hooks は、各論理スレッド、エージェント、およびツールのライフサイクル境界をレポートします。 Child プロセスは、プロセスの祖先、開始 ID、hook タイミング、およびスレッド証拠が一致する場合にのみスレッドにリンクされます。

したがって、supervisor は 3 つの所有権レベルを維持します。

| レベル | 証拠 | 許可されたコントロール |
| --- | --- | --- |
| 正確なスレッド child | child と論理スレッドは両方とも再検証されます | スレッド固有の論理制限。 すべてのガードが通過した場合の最終ローカル PID 一時停止 |
| アプリchild、スレッドは不明 | child は App Server に属していますが、確実に 1 つのスレッドに属しているわけではありません | 候補調査と最終層のみの最小可逆blind action |
| 共有 App Server | 複数のスレッドと共有メモリが 1 つのホスト プロセスを使用する | 観察と会計。 ホストは最後の保護段階としてのみ一時停止します |

プロンプト テキスト、会話の内容、モデル応答、および編集されたファイルの内容は、所有権を推測するために使用されません。

<a id="the-same-performance-policy-adapted-to-shared-memory"></a>
## 同じパフォーマンス ポリシーを共有メモリに適用

アプリ パスでは、CLI ポリシーの目標が維持されます。

- メモリ使用量が多くても安定している場合でも制限は発生しません。
- 十分な制動距離を備えた素早い変化は、即時のアクションを引き起こしません。
- 現在のheadroom、持続レート、自然圧力、および回復予備力までの時間が危険が近づいていることを示した場合にのみ行動が開始されます。
- 新しい展開は、進行中の編集、応答、結果の配信の前に閉じられます。
- 安定した回復の後、制限は徐々に再開されます。

App Server メモリは 1 回カウントされます。 daemon は、その常駐セット全体をオープンな会話間で均等に分割しません。 スレッドは、その hook および child アクティビティによってサポートできる増加のみを受け取ります。 残りの共有量は未割り当てのプールに残ります。 これにより、別のスレッドまたは共有ホストが増大したという理由だけで、アイドル状態のスレッドが非難されることがなくなります。

<a id="control-ladder"></a>
## 制御ラダー

supervisor は、App Server に合わせてアクチュエーターを変更しながら、CLI ポリシー順序を再利用します。

1. **観察します。** 軌道が回復可能である間は、すべての作業を開いたままにしてください。
2. **新しい拡張を遅らせます。** 計算された境界付近では、新しいエージェント、重いツール、ビルド、テストのみを保持します。 既存の出力と結果の配信は継続されます。
3. **一度に 1 つの論理ターゲットを絞り込みます。** 1 つのスレッドが原因としてサポートされている場合は、そのスレッドの今後の作業を少しずつ減らし、ステップごとに再測定します。
4. **候補 child を 1 つ選択します。** 現在成長しており、所有権の証拠が最も強い、最近の child を優先します。 選択されていないスレッド、エージェント、および実行中の作業は変更されません。
5. **必要に応じて、検証済みの child を一時停止します。** これは、論理制御が不十分で危険が差し迫ったままである場合の、可逆的な最終的なバックストップです。
6. **正確な所有権が利用できない場合にのみ、blind App コントロールを使用します。** 候補プールを調査し、最大 1 つの条件を満たすアプリ child に対して動作し、再測定し、軌道が改善した場合は直ちに停止します。
7. **共有 App Server を最後の保護段階としてのみ一時停止します。** これは、そのプロセスによってホストされるすべての会話に影響するため、アプリに起因する持続的な成長、差し迫った危険、失敗した下位層、永続的なアクションの記録、および使用可能な通知ルートが必要です。

普通の会話を 1 回しただけでは、このはしごをスキップすることはできません。 セッション数はブレーキをかける理由にはならず、安定した軌道にある 1 本の軽いスレッドは無制限のままです。

<a id="blind-control-and-its-limit"></a>
## Blind control とその制限

App Server は、すべての論理エージェントまたはツールの信頼できるオペレーティング システム PID を常に公開するとは限りません。 所有権が不完全な場合、supervisor は既知のスレッドがすべての共有メモリを所有しているかのように振る舞いません。 プロセスの祖先、作成時間、最近の hook アクティビティ、メモリ増加、ワークロード クラス、以前のアクション、および App Server 世代を使用して候補を絞り込みます。

Blind control は、選択したアプリ child のさらなる成長を止めることができますが、どの論理的な会話がその一時停止を感じるかは保証できません。 そのため、正確なスレッド制御よりも遅く、より保守的になります。 アクション ガードを満たす候補がない場合、supervisor は、推測された PID を通知する代わりに、アクションを admission の制御に保ちます。

<a id="lead-awareness-notifications-and-recovery"></a>
## Lead 認識、通知、および回復

ターミナルと有効なOS・リモート通知経路には、実際の保護措置が始まったときと完全に解除されたときに通知が届きます。影響を受けた論理leadは、次のhook境界で同じ理由と現在の復旧状態を受け取ります。

メモリ逼迫を理由に一時停止されたchildrenは、headroomが安定すると一つずつ再開します。自身のメモリが増え続けたために一時停止されたleadまたは共有App Serverは、保護付きで一度だけ試験的に再開されます。同じ増加が再発した場合、supervisorは自動再開を繰り返さず、もう一度一時停止してユーザーの判断を待ちます。

hook が無効になっているか、信頼されていない場合、または古いパスを介してルーティングされている場合でも、daemon は引き続きシステムおよびプロセス メモリを監視できますが、論理コントロール サーフェスの一部が失われます。 保護の低下を報告し、ユーザーに Codex App **設定 → Hooks** を確認するよう指示します。 スレッドの欠落証拠を黙って広範なプロセス制御に置き換えるのではありません。

<a id="multiple-windows-app-server-generations-and-federation"></a>
## 複数のウィンドウ、App Server 世代、および federation

1 つの App Server に接続されているすべてのウィンドウは、1 つのローカル アプリ サーフェスです。 メモリは 1 回カウントされ、各論理スレッドはその識別子によって重複排除されます。 App Server が再起動すると、新しいプロセス開始 ID によって新しい世代が作成されるため、古いプロセスからの古い所有権はシグナルを承認できません。

同じ論理スレッドを同時に要求する 2 つの App Server プロセスは、異常な衝突として扱われます。 supervisor は、曖昧さがなくなるまで、物理的な所有権をマージしたり、正確なスレッド制御を実行したりしません。

同じカーネル内で実行されている Codex CLI と Codex Desktop App は、同じローカルの daemon によって監視されます。 CLI プロセス ツリーと共有 App Server は別個のローカル サーフェスです。 コンピューターが WSL2、コンテナー、または動的ゲストも実行している場合、federation は、カーネル間で集約された新しい作業の決定を共有します。 アプリのスレッド制御や PID 権限を別の環境にエクスポートすることはありません。
