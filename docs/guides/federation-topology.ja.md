# 1 台のマシン上の環境全体で Federation

<p align="center">
  <a href="federation-topology.md">English</a> · <a href="federation-topology.ko.md">한국어</a> · <a href="federation-topology.zh-CN.md">简体中文</a> · <strong>日本語</strong>
</p>

Memory Supervisor は、独自のプロセスを確認および制御できる各オペレーティング システム カーネルで 1 回実行されます。 Federation を使用すると、複数のカーネルが同じ物理メモリをめぐって競合するときに、これらのスーパーバイザを調整できます。

<a id="the-deciding-rule"></a>
## 決定的なルール

2 つの環境は、両方の条件が true の場合にのみ連携します。

1. メモリは同じ物理 RAM に対して増加する可能性があります。 そして
2. 彼らは同じマシン上にいることを証明するホストローカル共有ディレクトリを通じて会うことができます。

Federation は現在の新しい仕事の決定を共有します。 メモリをプールしたり、作業を移動したり、あるカーネルに別のカーネルのプロセス ID に対する権限を与えたりすることはありません。

<a id="topology-matrix"></a>
## トポロジーマトリックス

| 環境 | ホストRAMを動的に共有しますか? | Federation の動作 |
| --- | --- | --- |
| ネイティブ Linux、macOS、または Windows | 2 番目のカーネルはありません | ローカル supervisor のみ |
| WSL2 とその Windows ホスト | はい | ホスト ファイル システムを通じて会議し、admission を共有します |
| いくつかの WSL2 ディストリビューション | はい | 同じホスト ファイル システムを介して会議を行う |
| ホストコンテナと通常のコンテナ | はい | 同じホストローカルディレクトリがマウントされている場合のフェデレーション |
| バルーンデバイスを備えたダイナミックメモリ VM | はい | ホストとローカルの共有フォルダーが利用可能な場合にフェデレーションを行う |
| 固定メモリ VM | いいえ; メモリがパーティション化されている | ゲストは独立した状態を保ちます |
| クラウド VM または別の物理コンピューター | 管理可能な共有RAMがない | 各マシンは独立したままです |

両方のコンピュータが同じネットワークの場所にアクセスできるという理由だけで、2 台目のコンピュータが federation ピアになることはありません。 ネットワーク共有は、物理メモリの共有を証明するものではありません。

<a id="detection-and-rendezvous"></a>
## 検出とランデブー

トポロジ アダプターは、次の 3 つの質問に分かれます。

```text
OS adapter          -> how this kernel measures memory and controls a verified local PID
AI adapter          -> how Claude Code or Codex exposes sessions, agents, and tools
topology adapter    -> which co-resident kernels share RAM and where they exchange state
```

WSL2 は、マウントされた Windows ホスト ファイルシステムを使用します。 コンテナーは、明示的にマウントされたホストローカル ディレクトリを使用します。 動的 VM は、使用可能なハイパーバイザー共有フォルダーを使用します。 それ以外の場合はローカルのみのままです。 Linux ゲストは、サポートされているメモリバルーン デバイスが存在する場合は動的として分類され、存在しない場合は固定として分類されます。

`memory-status --all` は、検出された環境とそれぞれの環境による決定を示します。 鮮度ウィンドウ内でリフレッシュされた状態のみが参加します。

<a id="what-crosses-the-boundary"></a>
## 境界を越えるものは

フェデレーション状態には、保護を調整するために必要な情報のみが含まれます。

- メモリ容量、headroom、圧力、レート。
- 現在の admission と回復状態。
- 診断に必要な環境、プロセス、端末、および論理エージェントの識別子。
- hook 接続の健全性と保留中のインシデントの状態。

これには、プロンプト、会話、モデル応答、プロジェクト ファイルの内容、完全なコマンド ライン、資格情報、または通知シークレットは含まれません。 各 supervisor は、自身のカーネル内で再検証するプロセスのみを一時停止または再開できます。

<a id="host-local-safety-check"></a>
## ホストとローカルの安全性チェック

ランデブー ディレクトリは物理ホストに対してローカルである必要があります。 Linux はネットワーク ファイルシステム タイプを拒否しますが、WSL2 のホスト ファイル システムなどのホスト ローカル マウントは許可します。 macOS にはローカル ファイルシステム フラグが必要です。 Windows は UNC パスとマップされたリモート ドライブを拒否します。

トポロジまたはディレクトリがあいまいな場合、supervisor は、リモート ピアの可能性を信頼する代わりに、環境を分離します。 その結果、調整が失われる可能性がありますが、別のマシンでのプロセス制御は失われません。

<a id="multi-terminal-behavior"></a>
## 複数端末の動作

1 つのカーネル内の複数の端末は、同じローカル supervisor によってすでに監視されています。 追加のデーモンを作成したり、メモリ合計を重複させたりすることはありません。 Windows、WSL2、コンテナ、または動的ゲストが同じマシン上に別のカーネルを追加した場合、各カーネルは独自の supervisor を実行し、federation は新しい作業の決定のみを調整します。

最悪の新しい admission 状態が共有リソースを管理します。 プロセスの封じ込めはローカルかつ選択的なままです。supervisor がピア環境の PID に信号を送信することはありません。
