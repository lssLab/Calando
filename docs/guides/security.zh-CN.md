# 安全和数据/控制边界

<p align="center">
  <a href="security.md">English</a> · <a href="security.ko.md">한국어</a> · <strong>简体中文</strong> · <a href="security.ja.md">日本語</a>
</p>

本文档列出 Calando 在一台计算机上本地读取、存储和跨环境共享的每一类信息，以及可选通知使用的网络访问和准确的控制范围。下表就是产品完整的数据和控制边界，表外的信息和程序不会被处理。

| 区域 | 它读什么或做什么 | 显式存储、共享和控制边界 |
| --- | --- | --- |
| 系统内存 | 读取操作系统的物理内存、可用内存和已提交内存的总计； 下降率； 记忆压力； 回收、交换和分页活动； 以及适用的容器内存限制。 | 它不会读取内存内容或更改 RAM、交换、容器限制或虚拟机内存设置。 |
| 正在运行的进程 | 读取当前权限级别可见的可执行文件和命令行元数据、PID、父关系、启动标识、终端、内存使用情况和增长率，以识别Claude Code、Codex及其child工作。 | 它不会读取进程内存内容或程序打开的文件，并且不会将完整的原始进程命令行保留在状态中。 对于 Chrome 或 IDE 等不相关的程序，它仅读取归因所需的操作系统进程元数据，并且不控制它们。 |
| Claude Code 和 Codex hooks | hook程序瞬时接收每个事件JSON，然后仅提取提供者、hook事件、会话、对话线程、代理、回合、任务和工具标识符和类型； App Server路由数据； 工作目录； 至多要启动的命令的前 2,048 个字符； 和限制收据。 | 即使事件包含提示、对话或模型文本或用于编辑的文件内容，这些字段也不会用于控制或放入本地状态、federation 或 Telegram 通知中。 它不会查询 Claude 或 ChatGPT 凭证存储或令牌。 直接在命令行上输入的机密可能会出现在提取的本地命令前缀中，因此不应将机密放置在命令行上。 |
| 本地存储 | 在用户配置文件下存储配置、内存决策、进程和代理状态、操作和恢复历史记录、hook 运行状况以及通知设置。 | 它不会写入项目文件。 原始工作目录和命令前缀只保留在本地，不会通过 Telegram 发送。 |
| 同机federation | 每个环境都会发布当前的记忆、压力、动作状态； 进程、终端和代理标识符； 应用程序hook路径和健康； 以及事件和恢复状态到同一本地共享文件夹。 节点仅使用十秒内刷新的状态来对齐新工作admission。 | 每个监视器仅控制其自己环境中的进程。 来自另一台物理计算机或云服务器的网络共享和状态不用于federation。 原始工作目录和命令前缀不包含在联合状态中。 |
| 网络和通知 | 正常监控不发出外部请求。安装和更新（包括每天一次的自动更新检查）从 GitHub 下载文件。开启 Telegram 后，会发送精简的内存状态、环境名和措施；设置命令会访问 Telegram Bot API。 | 该项目没有收集服务器或使用遥测。 机器人令牌保留在本地配置中，状态输出中不会显示。 不发送提示、对话文本、原始命令和项目文件。 |
| 新作品控制 | 在启动之前，hooks可以允许或延迟新的subagent、工具、构建、测试或其他高内存命令，并逐步缩小所选代理的未来工作范围。 | 它不会取消正在进行的编辑、响应或结果交付，也不会在终端中键入命令。 |
| 过程控制 | 仅作为最后手段，暂停一个重新验证为属于Claude Code或Codex的本地工作进程，然后在稳定恢复后一次恢复一个进程。 它会在执行操作之前立即重新检查 PID 并启动身份。 | 它从不终止或强制终止进程，也不会暂停另一个环境中的程序或 PID。 |
| Lead-代理保护 | lead仅在极少数情况下才会暂停，即在分阶段的新工作延迟和subagent和工具控制之后仍然存在危险，并且从同一lead持续增长，其确切过程和终端均已得到确认。 | lead 暂停不是普通的内存压力操作； 这是最后的保护阶段。 如果lead所在终端无法收到通知，则不会暂停。 |
| 终端和主代理通知 | 将限制和恢复状态的原因写入已验证的终端，并将相同的决定传递到下一个hook到lead。 | 它不读取终端输入、注入命令或更改终端设置或输入模式。 |
| 安装、更新和删除 | 仅安装、刷新或删除其用户范围的可执行文件或源、用户后台服务和自动启动条目、拥有的 hook 和技能连接以及配置和状态文件。 | 它不会修改项目文件、内核、驱动程序、防火墙或操作系统内存和交换设置。 只有用户运行 `uninstall` 时才会删除。自动更新只替换 Calando 自己的文件。 |
| 用户选择的设置 | 默认没有固定内存上限。`cap`、`on`/`off`、`update auto`、`lock` 和 Telegram 设置只在用户（或用户的代理）运行相应命令时改变。 | 不会自动开启上限。 |
| 保障措施 | 丢失或过时的hook决策将被丢弃，工作将通过，并且报告保护不可用。 在过程控制之前重新检查 PID 和启动标识。 lead 不会暂停，除非其确切终端可以收到通知； 如果动作记录无法保存，则不会保持暂停状态。 | 它不会留下阻碍工作的陈旧决策或保留未记录的暂停。 自动物理动作永远不会超过已验证的Claude Code或Codex工作流程的可逆暂停。 |

**Calando 只检查和控制此表中列出的内容。** 它不直接打开项目文件或处理内存。 可能到达hook事件内部的提示、对话、模型响应和文件内容字段不会被提取或用于控制，也不会保留到本地状态、通过federation共享或在外部通知中发送。 浏览器和 IDE 内部数据以及 Claude 或 ChatGPT 凭据也在其边界之外。

<a id="isolation"></a>
## 隔离边界

- federation 对等环境只有在其 `instance` 是普通标识符（字母、数字、`.`、`-`、`_`，最多 128 个字符）且与文件名相同时才会被接受。对等环境的文本不会进入代理上下文。
- hooks 以用户自己的权限运行。Calando 不会替调用者做调用者本来做不到的事。同一用户的代理可以配置 Calando，这是有意设计，便于代理帮助用户。
- `calando lock` 是阻止同一用户的代理关闭 Calando 的唯一方法。它是只有管理员能修改的策略文件（`/etc/calando/lock` 或 `%ProgramData%\Calando\lock`），不是沙箱：没有沙箱的同一用户进程仍然可以停止服务或伪造 federation 文件。伪造的文件最多只能暂缓新工作，效果与该进程自己占用内存相同。
- 在 WSL 中，`/mnt/c` 对发行版内所有 Linux 用户可读可写，因此 WSL 中的 Linux 用户之间不构成隔离边界。
- 发布文件附带 SHA-256 校验和与 GitHub 构建来源证明（attestation）。
