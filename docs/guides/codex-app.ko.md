# Codex Desktop App 감독 방식

<p align="center">
  <a href="codex-app.md">English</a> · <strong>한국어</strong>
</p>

Codex Desktop App은 Codex CLI와 같은 보호 정책을 사용하지만 프로세스 구조는 다릅니다. 이 문서는
무엇을 정확히 측정할 수 있는지, 어디까지 대상을 특정할 수 있는지, App Server가 충분한 소유권
정보를 주지 않을 때 어떻게 보수적으로 제어하는지 설명합니다.

## CLI와 Desktop App의 프로세스 구조 차이

CLI 세션은 보통 하나의 리드 프로세스와 그 하위 프로세스 트리를 가집니다. 따라서 하나의 로컬 실행
단위로 측정하고 마지막에 다시 확인할 수 있습니다. Desktop App은 여러 대화를 App Server 프로세스
하나를 통해 실행하는 것이 일반적입니다.

각 대화는 논리 스레드 번호로 나뉘며 Hook 판단에서는 독립 리드로 관리됩니다. 하지만 운영체제
프로세스까지 대화별로 하나씩 생기는 것은 아닙니다.

```text
Codex Desktop App
        │
        ▼
공유 App Server 프로세스와 공유 메모리
        │
        ├── 논리 스레드 A ── 에이전트와 도구
        ├── 논리 스레드 B ── 에이전트와 도구
        └── 아직 소유 대화를 확인하지 못한 App 작업
```

같은 대화를 다른 창에서 열어도 논리 리드가 하나 더 생기지 않습니다. 다른 대화를 열면 별도 논리
스레드가 되지만 두 대화는 여전히 같은 App Server 메모리를 사용할 수 있습니다.

## Supervisor가 확인하는 정보

로컬 데몬은 App Server를 감지하고 그 메모리를 한 번만 기록합니다. Hook은 각 논리 스레드,
에이전트와 도구의 시작·종료 경계를 전달합니다. 하위 프로세스는 부모 관계, 시작 정보, Hook 시점과
스레드 증거가 일치할 때만 특정 스레드 소유로 연결합니다.

따라서 소유권을 세 단계로 나눕니다.

| 단계 | 확인된 증거 | 허용되는 제어 |
| --- | --- | --- |
| 정확한 스레드 하위 작업 | 하위 프로세스와 논리 스레드를 모두 다시 확인 | 해당 스레드의 논리 제한, 모든 보호 조건을 통과한 경우 최후의 로컬 PID 일시정지 |
| App 하위 작업, 스레드는 불확실 | App Server 소속은 맞지만 특정 스레드 소유라고 보기 어려움 | 후보 조사, 마지막 단계에서만 가장 작은 가역적 blind 조치 |
| 공유 App Server | 여러 스레드와 공유 메모리가 한 프로세스를 사용 | 관찰과 합산, 모든 하위 단계가 부족할 때만 최후의 host 일시정지 |

프롬프트, 대화 내용, 모델 응답과 편집 파일 내용으로 소유권을 추측하지 않습니다.

## 공유 메모리에 맞춘 성능 정책

App 경로도 CLI 정책의 목적을 그대로 지킵니다.

- 메모리 사용량이 높아도 속도가 안정적이면 제한하지 않습니다.
- 감소 속도가 빨라도 안전하게 멈출 거리가 충분하면 바로 조치하지 않습니다.
- 현재 여유, 지속 속도, 운영체제 압력과 복구 기준까지 남은 시간을 함께 계산해 실제 위험이
  가까워질 때만 조치를 시작합니다.
- 진행 중인 편집·응답·결과 전달보다 새 에이전트와 새 무거운 작업을 먼저 미룹니다.
- 여유가 안정되면 제한을 단계적으로 다시 엽니다.

App Server 메모리는 한 번만 합산합니다. 전체 사용량을 열린 대화 수로 똑같이 나누지 않습니다.
Hook과 하위 작업 활동으로 뒷받침되는 증가량만 해당 스레드에 연결하고, 나머지는 소유 대화를 모르는
공유량으로 남깁니다. 다른 대화나 공유 host가 커졌다는 이유로 쉬고 있는 스레드를 원인으로 잡지
않기 위해서입니다.

## 단계적 제어 순서

Supervisor는 CLI 정책의 순서를 유지하면서 App Server에 맞는 수단을 사용합니다.

1. **관찰** — 현재 속도로 복구 가능한 동안 모든 작업을 그대로 둡니다.
2. **새 확장 대기** — 계산된 경계가 가까워지면 새 에이전트, 무거운 도구, 빌드와 테스트 시작만
   미룹니다. 진행 중인 결과 전달은 유지합니다.
3. **논리 대상 하나씩 축소** — 특정 스레드가 원인이라는 증거가 있으면 그 스레드가 앞으로 할 일만
   작은 단계로 줄이고 매 단계 뒤 다시 측정합니다.
4. **하위 작업 후보 하나 선택** — 현재 증가 중이고 무거우며 최근 시작됐고 소유권 증거가 강한
   후보를 우선합니다. 선택되지 않은 스레드·에이전트와 실행 중인 작업은 그대로 둡니다.
5. **필요한 경우 확인된 하위 작업 하나 일시정지** — 논리 조치로 부족하고 위험이 계속 임박한 경우에만
   사용하는 가역적인 마지막 안전장치입니다.
6. **정확한 소유권이 없을 때만 blind App 제어** — 후보군을 조사한 뒤 조건을 만족하는 App 하위
   작업을 최대 하나만 조치하고 다시 측정합니다. 상황이 좋아지면 바로 멈춥니다.
7. **공유 App Server 일시정지는 최후의 보호 단계** — 그 프로세스가 맡은 모든 대화에 영향을 주므로,
   지속적인 App 원인 증가, 임박한 위험, 앞 단계의 부족, 조치 기록과 알림 경로가 모두 확인된 경우에만
   사용합니다.

대화가 하나뿐이라고 이 순서를 건너뛰지 않습니다. 세션 수 자체는 제동 이유가 아니며, 가벼운 대화
하나가 안정적으로 실행되는 동안은 제한하지 않습니다.

## Blind 제어의 의미와 한계

App Server는 논리 에이전트나 도구마다 믿을 수 있는 운영체제 PID를 항상 제공하지 않습니다. 소유권이
불완전하면 확인된 스레드에 공유 메모리를 전부 떠넘기지 않습니다. 프로세스 부모 관계, 생성 시각,
최근 Hook 활동, 메모리 증가, 작업 종류, 이전 조치와 App Server 세대를 함께 사용해 후보를 좁힙니다.

Blind 제어는 선택된 App 하위 작업의 추가 증가를 멈출 수 있지만 어느 논리 대화가 영향을 받을지
완벽하게 보장할 수는 없습니다. 그래서 정확한 스레드 제어보다 늦고 보수적으로 사용합니다. 조치
조건을 만족하는 후보가 없으면 추측한 PID에 신호하지 않고 새 작업 대기 단계에 머뭅니다.

## 리드 인지, 알림과 복구

실제 보호 조치가 시작되거나 완전히 복구되면 터미널과 사용자가 켠 OS·원격 알림 경로에 한 번씩
알립니다. 영향을 받은 논리 리드는 다음 Hook 시점에 같은 이유와 현재 복구 상태를 전달받습니다.

시스템 압력으로 일시정지한 하위 작업은 여유가 안정된 뒤 하나씩 재개합니다. 자체 증가 때문에
멈춘 리드나 공유 App Server는 보호된 시험 재개를 한 번 받습니다. 같은 증가가 다시 나타나면 다시
멈추고 사용자의 판단을 기다리며 자동 재개를 반복하지 않습니다.

Hook이 비활성·미신뢰 상태이거나 오래된 경로를 가리키면 데몬은 시스템과 프로세스 메모리는 계속
관찰하지만 논리 제어 일부를 잃습니다. 이때 보호 저하를 표시하고 Codex App의 **설정 → Hooks**를
확인하도록 안내합니다. 사라진 스레드 증거를 넓은 프로세스 제어로 조용히 대체하지 않습니다.

## 여러 창, App Server 세대와 Federation

App Server 하나에 연결된 모든 창은 로컬 App 표면 하나입니다. 메모리는 한 번만 합산하고 같은 논리
스레드 번호는 중복으로 세지 않습니다. App Server가 재시작하면 새 프로세스 시작 정보를 새 세대로
기록하므로 이전 프로세스의 소유권이 새 프로세스 조치 권한으로 이어지지 않습니다.

App Server 프로세스 두 개가 같은 논리 스레드를 동시에 주장하는 상황은 비정상 충돌로 처리합니다.
모호함이 사라질 때까지 두 프로세스의 소유권을 합치거나 정확한 스레드 제어를 하지 않습니다.

같은 커널에서 실행되는 Codex CLI와 Codex Desktop App은 로컬 데몬 하나가 함께 관찰합니다. CLI
프로세스 트리와 공유 App Server는 서로 다른 로컬 표면입니다. 같은 컴퓨터에 WSL2·container·동적
guest도 있으면 Federation은 커널 사이의 전체 새 작업 판단만 공유합니다. App 스레드 제어나 PID
권한을 다른 환경으로 넘기지는 않습니다.
