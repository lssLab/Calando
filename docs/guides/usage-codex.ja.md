## サポートされている契約

このコマンドが hook 機能が安定していて有効であると報告する場合、Memory Supervisor は Codex CLI **0.145.0 以降** をサポートします。

```bash
codex --version
codex features list | grep '^hooks'
codex update
```

インストーラーも同じチェックを実行します。 サポートされていない、または無効になっている - hook リリースは、Memory Supervisor Codex hook なしで残されます。 以前に所有していた hook は再インストール時に削除されるため、ダウングレードによって暗黙的に保護を主張することはできません。 `codex update` が元のインストール方法で利用できない場合は、同じパッケージマネージャーまたはインストーラーを使用して Codex をアップグレードし、`memory-supervisor update` を実行します。

現在のCodex hooks は、`PreToolUse` を通じてローカル機能ツールを監視できます。 バージョン 0.145.0 では、オプションの subagent ID がスレッドスポーン hook 入力に提供され、ルート スレッドでは省略されます。 インストールされたマッチャーは意図的に広範囲に設定されているため、入力を意識した分類により通常の作業を維持できます。

```text
.*
```

アダプティブ admission `GREEN` または `YELLOW` では、新しい拡張はサイレントで許可されます。 `ORANGE` または `RED` では、実際の拡張呼び出しのみが回復を短時間待機し、その後、`ADMISSION_DEFERRED` で有効な拒否決定を返します。 論理 child 状態は、機密に分類された将来の拡張、ハイメモリの開始、広範な検出、または実稼働ワーク クラスのみを個別に拒否できます。 生の利用色は赤色のままで、アダプティブ admission により安定した作業が可能になります。 結果、メッセージ、ステータス、停止/キャンセル、および回復は、どの状態でも引き続き利用できます。

公式契約参照:

- [Codex hooks とツールの対象範囲](https://learn.chatgpt.com/docs/hooks)
- [Codex 高度な構成](https://developers.openai.com/codex/config-advanced#hooks)

## 設置と信頼

README の 1 行インストーラーを実行します。 supervisor がすでに存在し、後で Codex がインストールされた場合は、`memory-supervisor update` を実行します。 次に、通常の Codex コマンドを使用します。

```bash
codex
codex exec "your task"
```

`CODEX_HOME` が設定されている場合、hook は `$CODEX_HOME/hooks.json` にマージされ、それ以外の場合は `~/.codex/hooks.json` にマージされます。 無関係なグループは保持され、アトミック置換の前に以前のファイルがバックアップされます。 Codex は、管理されていない hook が新しい場合、またはその定義が変更された場合、レビューと信頼が必要です。 ユーザーは対話型 CLI セッションで個人的に `/hooks` を開き、正確な現在のコマンドを確認して信頼し、無効になっているエントリを有効にする必要があります。 インストーラーはユーザーの決定を自動化することはなく、Codex の再起動がユーザーの決定に代わることはありません。

その `/hooks` アクションは Codex CLI に属します。 Codex Desktop App では、ユーザーは **設定 → Hooks** で同じ手動決定を行います。 そこで有効化または信頼の変更を適用すると、共有 App Server によってすでにロードされているすべてのタスクの hook 構成が再ロードされます。 既存のタスクを次のリクエストで続行します。 新しいタスクやアプリの再起動は必要ありませんが、すでに発生した `SessionStart` は再生されません。 逆に、CLI `/hooks` 保存はその CLI プロセスを更新しますが、個別に実行されているデスクトップ アプリは更新しません。また、アプリ設定の保存は、実行中の他の CLI プロセスを更新しません。 両方のサーフェスがすでに実行されている場合は、最初にアプリ設定で承認を保存し、作業後に既存の CLI プロセスのみを再起動します。 承認が他のプロセスによって書き込まれ、現在のサーフェスに保存する実際の変更がない場合は、既に実行中のアプリまたは CLI を 1 回再起動して、共有信頼レコードを読み取ります。

Memory Supervisor は、所有する 7 つのイベントを 1 つの接続契約として扱います。 `memory-status --connections` は、各イベントの定義、有効な状態、および正確な現在の信頼ハッシュをチェックします。 したがって、欠落、重複、無効、信頼できない、または変更されたエントリは、Codex `CONNECTED` として報告できません。また、Codex App ルートは、他の 1 つのイベントが最近受信を生成したというだけの理由で、`ACTIVE` として報告することはできません。 欠落している定義または古い定義には `memory-supervisor update` を使用します。 エントリを有効にするか信頼するには、`/hooks` を使用します。 成功した `SessionStart` は同じ監査を実行し、lead とユーザーの両方に残りのどのイベントが不完全で、次に何をすべきかを伝えます。

`memory-supervisor update` のたびに `memory-status --connections` を実行します。 Codex は、Supervisor リリース番号ではなく、現在の hook 定義に対する信頼を保存します。 したがって、同じコマンドによるバイナリのみの更新には再承認は必要ありません。 インストーラーがコマンド、マッチャー、または別のハッシュ フィールドを変更した場合、Codex はレビューのために新しい定義を報告するため、ユーザーは影響を受ける CLI またはアプリ サーフェスでそれを再度信頼する必要があります。 プロセスを再起動すると、同じ `CODEX_HOME` を共有する別のプロセスによって既に保存されている承認が再ロードされる場合があります。 その承認を生み出すことは決してできません。

生成された各 Codex コマンドには、それが属する絶対ソース `hooks.json` も含ま​​れます。 ゲートはそのソースを現在のプロセスの `CODEX_HOME` と比較します。 これにより、ある環境のユーザー hook が、別の Codex ホームでプロジェクト hook として再検出されたときに、再び行動することができなくなります。 他の OS ルートがインストールされていない場合、そのコマンド フィールドはクロスシェル エラーではなく有効な no-op になります。 意図的に共有された Windows/WSL `CODEX_HOME` は、それぞれの既存のネイティブ ルートを保持します。 各ローカル supervisor は、独自のルートと PID スペースのみを監査および制御します。 Federation はまだ新しい admission 状態のみを共有し、hook の所有権や環境間の PID 権限を共有することはありません。

ユーザーレベルのhooksは、プロジェクトの信頼とは独立して適用されます。 プロジェクト ローカル `.codex` hook レイヤーは信頼できないリポジトリでは無視されますが、このインストーラーはプロジェクト ローカル レイヤーに依存しません。 Codex は、すべての信頼できるソースから一致する hooks をマージします。そのため、上記のソース ガードはドキュメントのみの警告ではなく、インストールされたルートの一部です。

<a id="hook-events"></a>
## Hook イベント

| イベント | 目的 |
| --- | --- |
| `SessionStart` | 再開/クリア/コンパクト時にスタートアップ契約と未確認のインシデントを挿入 |
| `UserPromptSubmit` | プレッシャーや目に見えない中断/再開の出来事について警告する |
| `PreToolUse` | ローカル機能ツールを分類する。 マシン admission または正確な論理エージェント状態によって除外されたワーククラスの下の新しいファンアウトのみを拒否します |
| `SubagentStart` / `SubagentStop` | ライフサイクルを観察する。 start は同じ 12 秒の RED フォールバックのみを追加します |
| `PostToolUse` | 完了した作業を遅らせることなく、未確認のインシデントバージョンを配信する |
| `Stop` | 終了をブロックせずに現在の論理ライフサイクル レコードを閉じる |

ORANGE は、`SubagentStart` で既に承認されている worker を遅らせることはありません。 Codex にはツール後の協調スリープがありません。 RED の圧力は、プリスポーン admission と独立した PID バックストップによって処理されます。 インストールされたコマンド hooks はオプションの `statusMessage` を意図的に省略しているため、ルーチンの Pre/Post hook の実行では TUI に Memory Supervisor スピナー テキストが残りません。 目に見えるメッセージは、実際のアクションまたは目に見えないインシデントに対してのみ返されます。 既存のセッションに依然として永続的な `Running PreToolUse/PostToolUse hook` 行が表示される場合は、`memory-supervisor update` を再適用し、ハッシュが変更されていれば `/hooks` を確認してから、`/hooks` を閉じて、その CLI セッションを続行します。 すでに開いており、プロセスローカルのリロードを受け取らなかった他の CLI プロセスのみを再起動します。

すべてのコマンド ラッパーはフェール オープンになります。 daemon の欠落、古い状態、不正な形式の hook 入力、または Rust ゲートの故障では、拒否の決定は行われません。 OS daemon は引き続き独立したバックストップです。

Codexのhook信頼はハッシュ単位です。変更されたhookコマンドを再インストールすると、その定義は再び確認待ちになります。影響を受けるCLIプロセスで`/hooks`を開き、正確な定義を確認して信頼してください。保存すると、同じCLIプロセスが保持するセッションは設定を再読み込みします。新しいセッションが必要なのは`SessionStart`をもう一度実行したい場合だけです。supervisor daemonを再起動してもCodex自体は再起動しません。一時停止したCodex leadが再開すると、対象ターミナルへの正確な通知とOS・リモートアダプターは、同じプロセスが実際に増え続けた直接証拠と、別に推定した`agent|mixed|external|unknown`のマシン全体の帰属を区別し、次に起きることを説明します。hookは次のプロンプトまたはツール終了境界で同じ安全事象を一度だけ再通知しますが、その時点がOSレベルの再開と完全に一致するとは限りません。Codex自体を再起動した場合は、Codexのセッション復元機能を使います。Codexは新しいプロセスで履歴を復元し、インストール済みの`SessionStart` hookは未通知のリソース事象と現在のsupervisor判断を一度だけ自動注入します。`runtime.json`はリソース事象を保存するだけで、Codex自身の履歴復元機能を置き換えません。

<a id="verification"></a>
## 検証

リポジトリの検証チェック:

```bash
bash tests/run.sh
memory-status --connections
```

`tests/native_codex.rs` はさらに、公式バイナリを使用して検出を検証し、使い捨ての Codex プロセスでネイティブのサスペンド/再開をラウンドトリップします。 オプトインカナリアを次のように実行します。

```bash
MEMORY_SUPERVISOR_NATIVE_CODEX_SMOKE=1 \
  cargo +1.88.0 test --test native_codex -- --nocapture
```

残りの Rust 統合テストでは、最小バージョンと機能レポート、インストールされている hook の形状、オレンジ色の `Agent` 拒否、正確な端末のターゲット設定、および不正な形式または古いフェールオープンのケースを検証します。 App Server を起動せず、モデル認証されたエージェントの生成も必要としません。

自動チェックでは、サポートされる最小の Codex バージョンと hook コントラクトが固定されるため、パブリック実行可能ファイルがビルドされる前に機能状態またはコマンド形状の変更が検出されます。
